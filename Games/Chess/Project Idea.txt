Project:   Chess — Premium Browser Chess Platform

Act as a senior frontend engineer, chess-engine developer, UI/UX designer, and QA automation engineer. Build a complete, production-quality chess web application inspired by Chess.com, with an original visual identity and an advanced glassmorphism interface.

1. Strict technology requirements

Use ONLY:

HTML5 for structure.
CSS3 for layout, styling, animation, and responsive design.
Vanilla JavaScript (ES6+) for application logic and chess rules.
Native browser APIs for storage, audio, keyboard controls, and DOM interaction.

Do not use React, Vue, Angular, TypeScript, Tailwind, Bootstrap, jQuery, Node.js application frameworks, or frontend build systems.

Keep the application runnable directly in a modern browser. Use separate files:

index.html
styles.css
script.js
tests/unit-tests.html
tests/unit-tests.js
tests/integration-tests.html
tests/integration-tests.js
README.md

Testing may use browser-native JavaScript and a lightweight custom test harness. If an external chess rules library is used, explicitly justify it and ensure the core project still uses only HTML, CSS, and JavaScript. Prefer implementing a robust legal-move engine in vanilla JavaScript without dependencies.

Create a luxurious, futuristic chess interface with a dark navy, midnight blue, violet, and electric cyan palette.

Visual requirements:

Layered translucent glass panels using backdrop-filter: blur(...).
Subtle gradients, ambient lighting, radial glows, and soft shadows.
Fine borders with translucent white highlights.
Rounded panels, refined spacing, and elegant typography.
Animated background orbs and subtle particle effects implemented with CSS or vanilla JavaScript.
Smooth hover, active, focus, and transition states.
Chess pieces with attractive Unicode or locally available piece glyphs; avoid broken external assets.

Responsive desktop, tablet, and mobile layouts.
Accessible contrast, visible keyboard focus, and reduced-motion support.
Graceful fallback for browsers without backdrop-filter.

The design should feel like a premium chess product rather than a generic admin dashboard. Use CSS variables for colors, spacing, shadows, glass opacity, and animation timing.

4. Chess engine and rules

Implement a complete legal chess rules engine in vanilla JavaScript. Separate the rules engine from rendering and UI state.

The engine must correctly support:

Standard starting position and valid FEN loading/export.
Legal movement for all six piece types.
Captures and protection against capturing the opponent's king.
Check, checkmate, and stalemate.
Castling on both sides, with all restrictions enforced.
En passant.
Pawn promotion with a working piece-selection dialog.
Pins and moves that would expose one's own king.
King safety when in check.
Checkmate and draw detection.
Threefold repetition and the fifty-move draw claim.
Fivefold repetition and the seventy-five-move draw rule.
Insufficient mating material detection.
Correct move counters, turn tracking, castling rights, and en passant state.
Undo and redo that restore the complete position.
SAN algebraic notation and UCI move notation.
Move validation before any state mutation.

Never implement chess as basic piece movement alone. Every move must be checked for legality against the complete current position.

Use a clear internal board representation and pure functions wherever possible. Suggested public API:

createGame(fen)
getLegalMoves(position, square)
makeMove(position, move)
undoMove(history)
redoMove(history)
isCheck(position, color)
isCheckmate(position)
isStalemate(position)
getGameStatus(position)
getFen(position)
getSan(position, move)
parseSan(position, notation)
getCapturedPieces(history)
getMaterialBalance(position)

Use immutable snapshots or complete reversible move records. Undo and redo must preserve castling rights, en passant, half-move counters, full-move numbers, repetition history, and promotion details.

Implement accurate two-player chess clocks using a monotonic time source such as performance.now().

Include:

The unit and integration test pages must:

Run from a local static HTTP server.
Display pass/fail totals.
Identify each failed assertion.
Show expected and actual values.
Provide stack traces where available.
Use deterministic fixtures and mocked clocks.

Use a test registry and assertion helpers such as assertEqual, assertDeepEqual, assertTrue, assertThrows, and assertFenEqual.

Add a final regression suite that runs all core chess rules tests before declaring the build ready.

Phase 1: Create the file structure and polished responsive glassmorphism layout.
